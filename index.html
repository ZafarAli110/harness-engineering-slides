How the model works

Sampling: temperature, top-k and top-p

Sampling is how the next token is picked from the odds. Temperature reshapes the odds; top-k and top-p limit the candidates.

Temperature

How adventurous the pick is. At 0 it always takes the favourite; higher, it sometimes takes a less likely token.

e.g.0: the same answer every time
Top-k

Only the k most likely tokens may be picked; every other token is cut, however close it was.

e.g.k=3 → mat, windows, table survive
Top-p

Only the favourites whose odds add up to p may be picked, so the list grows or shrinks with the odds.

e.g.p=0.8 → maybe four

Why it mattersTemperature controls consistency, not truth. At 0, a wrong favourite is wrong every time.

CONTOUR SOFTWAREENGINEERINGM1 · LLM fundamentals
1. One distribution on the board: database 42, server 21, request 12, code 8, file 5. 2. Temperature: the height of the bars. 3. Top-k = 3: a fixed count (database, server, request). 4. Top-p = 0.8: a running total, here four. It adapts to how sure the model is: the usual default. 5. Kill "temperature = creativity": it only sharpens or flattens the odds. 6. If asked how it works: the model gives every token a score; softmax turns the scores into odds that add up to 100%. Top-k: sort, keep the k highest. Top-p: sort, add the odds from the top, stop at the token that takes the total to p or more (it is kept), drop the rest. Temperature: divide the scores by T before softmax (below 1 sharper, above 1 flatter, 0 = always the top). Then one weighted random draw among what is left. 7. Top-p does not pick; it decides who may be picked. E.g. "7" 76% and "3" 12%: p = 0.85 keeps both (88%), they are rescaled to about 86% and 14%, and the draw picks "7" about 86 times in 100. The local Qwen's llama-server (its /props) runs top_k, then top_p, min_p, then temperature; defaults k 40, p 0.95, T 0.8. Line to land: temperature 0 is no guarantee. Batching, hardware and floating-point order still vary; verification replaces that hope. If asked "can I set temperature in Claude Code?": no. Current Claude models reject temperature, top-k and top-p; since 21 Oct 2026 the API rejects them on every model. The dial is effort (/effort, default xhigh): how much it thinks first. More effort, more tokens.

What the model can and cannot do

The model and the app around it

A model turns text into text. Everything else is done by the app around it.

The model (GPT, Claude, Qwen)

  • Reads only the text it is sent: no files, no screen.
  • Writes text, sometimes a request to use a tool, such as read_file(tickets.csv).
  • Cannot run anything itself, not even that request.
  • Remembers nothing between calls.

The app (ChatGPT, Claude Code)

  • Chooses what to send: your message, files, rules, the history.
  • Reads files, calls APIs, runs commands.
  • Decides whether to carry out each request.
  • Keeps what must be remembered, and sends it again each call.

Why it matters“Claude read the repository” means the app chose files and sent them. The model only read the text.

When a model becomes an agent

A chat and an agent

The same model can sit in both. The difference is who decides the next step.

A chat, with history

  • You decide the next step.
  • You act: you fetch tickets.csv and paste it in.

The moment a model becomes an agent

The agent loop

workshop
 conversation = [your task]
 while (true) {   ← this loop makes it an agent
   // the model reads the whole conversation
   reply = model(conversation)
   conversation.add(reply)
 
   // the model decides when to stop: it answers
   if (reply is an answer) break
 
   // it asks for a tool: the app runs it
   result = app.run(reply.tool)
   conversation.add(result)
 } // repeat: the conversation keeps growing

That is it. An agent is a model in a loop, choosing each next step from what the app hands back. Claude Code, Copilot and Cursor run this same loop.

Why the agent got it wrong

A model does not calculate

It predicts each digit of an answer by its odds. Nothing adds anything up.

Short sums: right

Seen countless times in training, so the most likely answer is also the right one.

e.g.47 × 38 = 1,786
Long sums: wrong in the middle

It gets the start and the end right; the digits in the middle are a guess.

e.g.4,821 × 937: said 4,501,277, really 4,517,277
A small change moves the guess

Digits are predictions, not sums, so any change to the text can change them.

e.g.add one tool to the request: 158 becomes 178

Why it mattersBigger models slip less, but work the same way. Only a tool or a check proves it right.

Harness engineering

The harness

Everything around the model: the code that decides what it sees, what it may do, and whether its answer counts.

What it sees

Instructions and files, chosen for this task and put into the text the model reads.

e.g.RULES.md: never do sums in your head
